01 · CODE NEEDS SOMETHING TO RUN IT

Instructions are not the machine.

A JavaScript file is a set of instructions. On its own it does nothing. A runtime reads those instructions, carries them out, and talks to the surrounding computer.

Instructions JavaScript

The language: variables, decisions, functions, and requests such as “read this file.”

→
Executor A runtime

The program that interprets the instructions and provides abilities such as files, timers, and networking.

Motion analogy: an After Effects expression is instructions; After Effects is the environment that executes it. Likewise, JavaScript is instructions; Node.js or Bun can execute them outside a browser.
02 · FOUR THINGS PEOPLE OFTEN CALL “NODE”

Separate the language, runtime, terminal, and packages.

When these are blurred together, errors feel supernatural. When they are separate, most messages tell you which layer needs attention.

Runtime

Node.js

Runs JavaScript outside a browser. A Node process may read files, make network requests, run a server, then exit—or stay alive waiting for work.

CookieMonster uses

Bun

A Node.js-compatible runtime and toolkit. In this project, many commands begin with bun.

Controller

Terminal

A text interface that starts programs. It can launch Node or Bun, but it is not itself a JavaScript runtime.

Reusable parts

Packages

Other people’s or teams’ reusable code. The project manifest declares which packages and named commands belong to the job.

Production analogy: package.json is part call sheet, part equipment list. node_modules is the local equipment cage. npm or Bun is the runner who acquires what the list calls for.
03 · A MODEL IS NOT A CODING HARNESS

The brain needs a working environment.

A model can propose a next step in text. A coding harness turns that proposal into a controlled workflow around real files and real tools.

01

You

Set the objective, boundaries, references, and definition of done.

02

Harness

Builds context, applies rules, exposes tools, and records the session.

03

Model

Reasons over the context and chooses a next action or answer.

04

Tools

Read, search, edit, run commands, browse, or inspect outputs.

05

Project

The selected folder: source material, instructions, and changed files.

06

Evidence

Tool output returns to the harness so the model and user can assess it.

Studio analogy: the model is a creative problem-solver; the harness is the producer and production desk; the project folder is the job; tools are departments; permissions are approvals; tests, diffs, and previews are QC.
04 · COOKIE MONSTER, LAYER BY LAYER

One product, several jobs.

The important question is not “Is CookieMonster intelligent?” It is “Which layer is responsible for this part of the work?”

Desktop shell

Electron presents the windows, project picker, conversations, approvals, and results.

Harness

OpenCode manages sessions, project context, rules, agents, tools, and the action loop.

Model route

CookieMonster sends model work through the authenticated WPP Open bridge.

Local execution

Tools inspect or change the selected project. Bun runs much of CookieMonster’s JavaScript and TypeScript tooling.

The useful truth

CookieMonster is not simply “the AI.”

It is the working environment that connects your brief, an AI model, the correct project folder, controlled tools, and evidence.

model ≠ harness ≠ runtime ≠ terminal

05 · HOW A TURN ACTUALLY WORKS

It is a loop, not one magic answer.

A useful agent repeatedly gathers evidence and adjusts. The harness carries information between the model and the tools at each step.

Observe
Decide
Act
Inspect
Report or repeat
Motion analogy: brief → first pass → RAM preview → notes → revision → final check. You would not approve a film because an editor said “export complete”; you inspect the file. Treat agent output the same way.

07 · SIX HABITS BEFORE “SEND”

Safe use is a production habit.

These checks matter more than clever prompting.

01

Open the right folder

The selected project defines the practical boundary of the job.

02

State the outcome

Describe the deliverable, not merely a vague activity.

03

Set boundaries

Name what may change, what must not change, and any client-data constraints.

04

Choose the mode

Explore uncertain work in Plan. Use Build when an edit is intentionally required.

05

Read approvals

An approval is a real action boundary, not a nuisance dialog.

06

Demand evidence

Review the file, diff, preview, test, or exported artifact—not only the final prose.
