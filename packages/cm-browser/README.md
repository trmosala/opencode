# CookieMonster browser

The desktop browser uses main-owned Electron `WebContentsView` tabs. Tabs belong to a chat session and retain their pages when switching tabs, switching sessions, or hiding the browser panel. Closing a tab respects its `beforeunload` handler. Pop-ups open as new tabs and preserve normal opener behavior.

## Whole-tab Agent Access (#37)

One **Agent Access** grant authorises the selected native tab and all its documents, regardless of origin. Main owns the grant. Supported page operations, screenshots, diagnostics and site tools use it without another tool, receiving-origin or capture approval. Cross-origin navigation and redirects retain the grant but invalidate old document refs and pending source-bound captures.

Disable the tab grant or global access to cancel pending work and suppress late disclosure. Closure, renderer loss and owner replacement revoke authority. New, reopened, recovered and popup tabs start private; grants are not persisted or inherited. Revocation cannot recall content already delivered or effects already dispatched. Native busy/rendering leases remain held until dispatched work settles.

This changes authority, not driver capability. Issue #37 does not add frame discovery or interaction capabilities; those are tracked separately. Screenshots still require a selected, attached native view and disclose all visible pixels without redaction.

## Embedded documents and input (#39, #40)

An aggregate tab read includes bounded document records for native nested frames, including cross-origin, sandboxed and srcdoc documents. Each record identifies its frame and parent, reports read/truncated/unsupported/failed state and omission reasons, and carries its own opaque element refs. Open shadow content is readable. Closed roots, canvas and other nonsemantic rendered content require visual observation. Reading a clipped document does not establish that its controls are currently reachable by pointer input.

Click, hover, drag, fill, key, selection and scroll tools accept an explicit `frameRef` under the same tab grant. Main binds preparation to the exact action and current native document, verifies iframe ownership and supported affine geometry, and routes input to that document. Selection uses a fixed isolated script and emits untrusted DOM events. Perspective geometry is unsupported. Keyboard input requires the actual focused child frame; it never falls back to the top document. Use refs from the latest returned observation: old refs can expire as bounded snapshots are replaced. A failed observation after dispatch remains an uncertain outcome and never causes automatic replay.

The isolated `--embedded-documents` and `--embedded-input` fixtures use synthetic pages. Authenticated Teams calendar parity remains unverified; the running development instance has not been restarted with these changes.

## Bounded visual observation and input (#45)

Viewport screenshots reduce JPEG quality and resolution within a 46,080-byte image limit. Supported outputs retain at least half the captured raster and CSS viewport resolution and report actual dimensions, viewport dimensions and scale. A detailed image that cannot meet that limit at the supported minimum returns an explicit reason. Raster edges remain bounded to 4,096 pixels and total raster size to 4 megapixels. Screenshots include visible editable values without redaction.

A stable screenshot also supplies a one-use `visualRef`. `browser_visual_action` accepts click or hover coordinates in that returned raster. Main verifies native ownership, document identities, viewport/layout state, current pixels and native hit routing before dispatch. Navigation, layout changes, scrolling in any tracked document, revocation and reference reuse invalidate the action. Animated or unverifiable document tracking still permits a bounded screenshot but reports `actionUnavailable` and supplies no action ref. Static canvas and closed-root controls can use this path without another approval.

The isolated `--visual` fixture uses detailed synthetic pixels, canvas and closed-root controls, and a cross-site target with a confirmed out-of-process iframe session. These results do not establish authenticated-site, macOS or packaged-app qualification. Earlier capability and consent acceptance records below describe older implementations and are superseded by these current sections.

## Targeted inspection and waits

`browser_read_state` accepts an optional `selector` with an explicit `tabID`, and an optional native `frameRef`. It reads the first matching subtree with its own traversal and output budget, so a control omitted from an aggregate snapshot can receive a real ref. `inspection.matched=false` reports an absent match. A targeted read remains bounded and can report truncation; it does not search shadow roots by selector.

Selectors support one ASCII compound: an optional tag followed by `#id` or `.class` tokens, such as `button#open.primary`. The maximum is 512 characters. Whitespace, attributes, pseudos, escapes, combinators, universal selectors and lists are rejected.

`browser_wait_for_element` selects the top document or an explicit `frameRef`, accepts a timeout from 1 to 15000 milliseconds, and reports the actual `observedCondition`. `visible`, the default, requires positive viewport intersection and Chromium opacity/visibility checks. `attached` requires a connected match even when hidden. `ready` requires a match and a document whose readyState is interactive or complete. A successful wait returns a fresh targeted snapshot; it does not establish clickability or prove a new reload. Replacement, navigation, revocation and cancellation interrupt the wait.

The isolated Windows Electron fixture `bun scripts/browser-smoke.ts --targeted-read` covers recovery of an omitted 320th control, an absent match, delayed visible content, hidden attached content, cancellation and document replacement. `--embedded-documents` covers a native nested-frame wait. These fixture results do not establish authenticated Teams parity.

Vault access, OS permissions, native file selection, transfer rules, profile-wide history and tab lifecycle approvals remain separate. The grant is not permission to read saved credentials or choose local files automatically. The plugin and desktop must ship together. Historical acceptance records below describe earlier builds; their per-tool/per-origin/per-capture approval requirements are superseded by this section and are not current behavior.

## Using the browser

### Operation outcomes and recovery (#38, #43)

Page action results report `not_dispatched`, `dispatched_observed`, or `dispatched_uncertain`. The last status means native input may have taken effect without a confirmed refreshed observation. Typed action causes distinguish native dispatch failure, failed or unavailable observation, cancellation, timeout and unknown transport outcome. Observe the current tab before deciding on further input; the browser does not replay the action automatically.

Main publishes running, settling, failed and interrupted-input quarantine states separately from the Agent Access grant. Taking over revokes agent authority immediately, while already-dispatched native work keeps its busy lease until it settles. Renderer loss revokes access and publishes the crash reason; load failures retain Chromium's error code and description. Monotonic state revisions prevent delayed UI responses from clearing newer failures or running status.

An uncertain key or pointer down quarantines that native view. Reloading and granting access again cannot repair it. The recovery banner offers Close tab; reopen the saved URL/history through Recently closed or Control/Command+Shift+T. The new tab starts with Agent Access off. Unsaved form content is not restored, so closure still respects the page's leave confirmation.

Open the browser panel, choose **New tab**, and enter an HTTP(S) address or search terms. Searches use DuckDuckGo (`https://duck.com/?q=…`) by default; Browser settings can explicitly select Google or Bing. The fixed HTTPS templates accept only the encoded query value. Bare domains and local development addresses navigate directly regardless of the selected engine. Back, forward, reload, and stop work on the selected tab. URL, selected text, picked elements, and screenshots can be attached to the chat draft.

Within the browser, Control/Command+L selects the address bar, +T opens a tab, +W closes the tab (respecting unsaved-page confirmation), and +R reloads. Control+Tab switches forward and Control+Shift+Tab switches backward. Control/Command+Shift+T reopens the most recently closed tab. Recently closed tabs are also listed in History. New blank tabs focus the address bar.

The address bar suggests local history, bookmarks, and other tabs in the current task. Up/Down and Enter choose a suggestion; Escape dismisses it. Selecting an open tab switches to it without creating a duplicate. Pressing Enter without selecting a suggestion keeps normal direct-address/search behaviour. Suggestions make no network requests; only submitting search text contacts the selected engine.

Normal tabs and pop-ups keep the same Chromium user agent and actual engine version. Electron's fallback is also Chromium-based because its popup creation can ignore per-tab overrides (electron/electron#45897); this fallback is process-wide, while browser cookies and permissions remain partitioned.

Cookies use the separate persistent `persist:cm-browser` partition, shared by browser tabs but isolated from the app and WPP login. Pages have no Node integration or access to the desktop preload API. Restore tabs is enabled by default. Returning to a task restores its saved page URLs, selected tab and supported back/forward history, with fresh tab IDs and agent access off; the vault starts locked on app relaunch. Recovery keeps up to 32 tabs per task, 20 recently closed tabs per task, and 50 recently saved tasks. Navigation recovery retains at most 20 URL/title entries around the selected page, never Chromium form/page state or POST bodies. See [Browser recovery (#20)](#browser-recovery-20) for fallback and privacy limits. Turning Restore tabs off deletes saved recovery data; open tabs and in-memory recently closed tabs remain available until the window closes. Camera, microphone and notification permissions default to Block and can be configured per origin in Browser settings. Notification controls require native capability; screen sharing, clipboard permission controls and location remain unsupported.

Downloads use Electron's authenticated browser transfer. Browser settings can choose the destination folder and whether to show a native Save dialog (on by default). Transfers eligible for restart recovery use a private staging file and publish to the chosen folder with exclusive creation, selecting a numbered sibling if a name already exists. Other automatic downloads retain the existing reservation flow. An unavailable destination falls back to the Save dialog. Active initial downloads support pause, resume and cancel through Electron DownloadItem. Application cancellation does not delete user destination files. Chromium can independently remove its own transfer files.

Download admission is recorded before destination setup. Up to 200 admission/finished records persist, with current-process live transfers protected from automatic history pruning; a full live-transfer limit or failed admission write prevents saving. Reopening unfinished records never starts a request or restores consent. Filename search, timestamps and individual removal remain available. Show in folder requires a completed regular file matching available size and recorded metadata; this is not a content-integrity or atomic filesystem guarantee. Clearing download history leaves user destination files on disk but discards unreferenced private recovery files. Files are never opened automatically.

### Download recovery (#21)

Supported interrupted downloads offer **Resume saved download**. Each attempt requires a fresh native, default-cancel confirmation showing the initiating site, download server and original destination folder. Main rechecks current download rules for both origins. Recovery uses Chromium's authenticated `session.fetch` with the browser partition's current cookies, not saved authentication headers. The actual response must be HTTP 206 with matching strong ETag, Last-Modified, total length, exact Content-Range and identity encoding. Redirects, login failures and servers that ignore ranges fail without silently restarting from byte zero. Retry from the page remains available for unsupported transfers.

Initial eligibility requires a single HTTPS URL, or loopback HTTP for local development, known length and both validators. Recovery is not offered for redirected URL chains, weak/missing validators, unknown lengths, URL credentials, legacy history without checkpoints, or transfers interrupted before a checkpoint was saved. Original Save-dialog selection or automatic-folder preference supplies the destination; renderer commands supply only the record ID. Symlinked paths and replaced destination directories are rejected.

Checkpoints retain a SHA-256-validated copy of at most the first 64 MiB. They are refreshed at most every 30 seconds during progress, with a final attempt before cancelling an interrupted native transfer. A restart can therefore resume from an older prefix, not necessarily the last displayed byte count. Recovery streams the missing range into a separate private working file and publishes a new numbered file in the original folder without overwriting existing files. Recovered transfers have Cancel but no Pause control; cancelling explicitly discards their recovery record. Another crash retains the previous checkpoint. Private staging/working files and the final destination temporarily require extra disk space. Unreferenced private files are collected after transfers settle, history removal/clearing, or the next browser initialization.

The supported target is macOS. Run `bun scripts/browser-smoke.ts --download-recovery` from `packages/desktop` for the isolated crash/relaunch fixture. It uses only its own temporary profile, local server and child processes. See [download persistence safeguards](password-security.md#download-persistence-safeguards-21) for privacy and platform limits.

## Browser recovery (#20)

Electron `navigationHistory.restore({ entries, index })` restores supported URL/title-only stacks, including recently closed tabs. Entries are explicitly projected on both read and write; `pageState`, `history.state`, form values, POST bodies, grants and unknown fields are not carried into recovery. At most 20 entries around the active index are retained, from a validated stack of at most 100 entries with URLs up to 2,048 characters and titles up to 512. Unsupported or malformed navigation metadata falls back to the validated saved URL. Existing URL-only records, including longer URLs, remain supported without truncating addresses. Malformed stores/collections are rejected without overwriting them or caching an incomplete group.

Pending or failed restoration retains its saved snapshot. Failed Reload, HTTP 204 and Stop do not replace it merely because a request started; successful navigation updates it, and replacement/closure invalidates the old callback. Failed restoration points to the existing Reload, address and close controls; ordinary load errors retain their existing copy. No automatic retry is added.

Recovery metadata is local plaintext. Websites can put sensitive information in URLs or titles, so this projection is not general data-loss prevention. Restored pages issue requests and execute site scripts using the browser partition's existing cookies/storage; not replaying POST bodies does not make those page loads side-effect-free. Turn Restore tabs off to delete saved recovery metadata. No agent grants or vault authentication are restored.

From `packages/desktop`, `bun scripts/browser-smoke.ts --recovery` uses a temporary profile and loopback server, kills only its owned seed process after a checkpoint, then relaunches with the same profile. It checks selected history index, Back/Forward, recently closed tabs, fresh private IDs, vault locked before any unlock, no restored form/history-state values and zero POST requests on relaunch. It also covers legacy/malformed metadata, failed Reload, redirects, HTTP 204, Stop, stale completion after replacement/close, and malformed-store preservation. This is an isolated process-crash test, not physical power-loss, packaged-app, native accessibility, macOS/Linux or real-provider assurance. Authentication/dialog answers are fixture seams; the new recovery copy has English fallback pending reviewed translations.

The separate #20 stale-running task incident remains open. Legacy/V2 execution ownership is process-local and the shared database has no exclusive execution-owner boundary; an empty local runner map cannot prove another process's work abandoned. This slice neither settles persisted transcripts nor automatically resumes tools/providers/publication. Durable settlement needs an agreed cross-process ownership/fencing design; partial output, child links, completed side effects and pending admissions must remain intact.

## Links, bookmarks, and site controls

Browser settings choose separate destinations for app web links and local development links. Web links default to the system browser; localhost (including `.localhost`), IPv4 loopback and IPv6 loopback default to CookieMonster. An active task is required for internal routing; otherwise the system browser is used. Links followed inside browser pages retain normal in-tab navigation and popup behaviour. Right-click links in the app or browser to explicitly open in CookieMonster or the default browser. Internal links open a fresh tab with agent access off.

Tabs can be pinned, reordered within their pinned or unpinned section, duplicated, or closed in bulk. Pinned tabs stay at the left and bulk-close actions preserve them; they can still be closed individually. A duplicate is a fresh unpinned private tab at the current URL: it does not inherit agent access, native page state, device emulation, login operations, or the source tab's navigation stack. Left/Right, Home and End move keyboard focus and selection across the tab strip. Tab order and pin state use the existing URL/title-only recovery record, and every close still uses Chromium's `beforeunload` flow.

Bookmarks are local to the private browser profile, with up to 2,000 entries. Add the current page from the address toolbar; manage, edit, delete, order within a folder, and pin favourites in Bookmarks. Pinned entries appear on the new-tab page in stored order. Existing flat records migrate to the root folder without changing IDs, order or pin state. Folder paths support eight levels with 128 characters per segment; `›` separates levels in the editor and is therefore unsupported inside a folder name. Empty folders are not stored.

Import/export uses standard browser HTML bookmark files, parsed with `parse5` without executing scripts or fetching resources. Supported nested folder structure and traversal order survive round trips. Imports skip unsupported URLs, keep the first duplicate from the source, preserve existing normalized-URL duplicates including their folder and pin state, and append genuinely new bookmarks in import order. Imports are limited to 5 MB, 2,000 supported bookmarks and 500 folders. Export retains CookieMonster pin state in an optional HTML attribute. Clearing history does not remove bookmarks.

Site controls beside the address bar show whether the loaded page used HTTP or HTTPS, without treating HTTPS as a trust verdict. Chromium certificate failures remain blocked. Controls reuse the exact-origin camera/microphone settings, revoke current-tab agent access, and inspect/clear site data through Chromium APIs. Inspection reports the number of cookies matching the current page plus Chromium's aggregate origin-storage usage and nonempty quota-managed categories; it never returns cookie values or stored records. Chromium does not expose a reliable per-origin HTTP-cache size through Electron, so the UI does not invent one. Reopening Site controls refreshes the inspection, and a manual refresh is available for data changed while the panel stays open.

Storage and cache clearing are all-time and target the selected origin. Chromium removes cookies for the registrable parent domain, which can sign out sibling subdomains and may remove cookies beyond the matching-cookie count. The inline explanation and default-Cancel native confirmation state this scope; no time-range control is offered. Open pages at the exact selected origin reload after clearing. Sibling-origin storage, unrelated browser origins, app/WPP sessions, bookmarks, history, downloads, passwords and permission rules remain separate. From `packages/desktop`, `bun scripts/browser-smoke.ts --site-data` verifies Chromium inspection, exact-origin storage removal, parent-domain cookie removal, exact-origin tab reloads and preservation of sibling/unrelated records and isolated partitions with a disposable profile.

## Device preview (#24)

Show device toolbar exposes custom width/height from 160 to 4096 CSS pixels, named reusable size presets, Apply size, and Swap width and height. Presets persist in the private browser profile, are limited to 20 unique names, and contain dimensions only. Native emulation scales the preview to fit the panel, with device scale factor 1, unchanged page zoom and real Chromium identity. Page viewport metadata and zoom can affect layout. Swapping dimensions previews orientation layout, not device sensors; touch emulation is unavailable through this Electron API and mouse input is unchanged.

Each tab keeps its preview in memory across navigation and tab switches; resizing recalculates fit. Hide device toolbar restores the native baseline. Fresh, reopened and recovered tabs do not inherit preview settings, even when a named size remains available. Busy, loading, suspended, login, held-input and pending-close/reload targets reject changes. Changes invalidate stale snapshots, captures and consent without changing agent grants. Pending selection/picker/screenshot results cannot become valid again after switching away and back.

Zoom is stored for the exact HTTP(S) origin, including a non-default port, and is reapplied after navigation, in another open tab, and after URL/title-only recovery. Navigating to an origin without a rule explicitly restores 100%; Reset removes the current origin's rule. This uses Electron's Chromium zoom facility and does not emulate operating-system display scaling. Corrupt persisted zoom or preset collections are ignored for display and cannot be overwritten through the browser commands.

From `packages/desktop`, `bun scripts/browser-smoke.ts` covers preview and restoration; `--capture-selection` covers native capture round trips and `--offer-arming` covers the delayed-arming fixture regression. Run native variants separately and serially with disposable profiles. See [preview evidence and limits](password-security.md#device-preview-and-capture-24), including the unresolved historical login-offer cause, unsupported touch and platform/physical-validation limits.

## Browser menu and saved logins

The browser menu provides Chromium find-in-page (Control/Command+F), native printing (Control/Command+P), zoom, a configurable mobile preview (390 by 844 CSS pixels by default), screenshot-to-chat, downloads, history, imports, and browser data settings. Mobile preview retains the real Chromium user agent. History retains up to 2,000 recent visits across browser sessions, including repeat visits, with title/URL search, dates, individual deletion, and opening a visit in a new tab. Existing history rows receive stable IDs without inventing past visits. Recording can be disabled in Browser settings. The default search engine remains DuckDuckGo; missing, legacy DuckDuckGo, or invalid stored selections safely read as that default.

Password storage uses Node's AES-256-GCM implementation for an authenticated vault containing passwords, websites, usernames, and credential IDs. A fresh random key is protected with Electron `safeStorage` (Windows DPAPI, macOS Keychain, or the Linux secret store) on every write. It fails closed when OS encryption is unavailable, Linux falls back to `basic_text`, authentication fails, or a remote-debugging port/pipe is enabled. The general renderer storage API cannot access the private browser store. Browser history remains local plaintext. The agent browser tools have no vault API, and snapshots exclude editable values/content (not deliberately mirrored ordinary site text). See [Password security](password-security.md) for the threat model and outstanding assurance work.

Payment-card autofill, CookieMonster-managed passkeys, and cross-device sync are not supported. Their separate discovery proposals and acceptance gates are recorded in [Future credential and sync proposals](future-credential-proposals.md); no implementation or placeholder controls are authorized by that document.

**Passwords and autofill** can save a filled login before submission and fill a saved login on its exact origin, with agent access off. Saving and filling each require native confirmation naming the website and username. It never submits the form. Combined filling requires a single visible, unobscured password field and an unambiguous username field in the main document. Explicit username-only and password-only actions support multi-step logins on the same saved origin; username-only filling requires a uniquely identified username/email field. Each mode sends only its requested field to the page, over HTTPS (or HTTP loopback for development). Forms must use POST and same-origin submission destinations; form-less JavaScript logins are supported. Navigation, replaced fields, new-password fields, or concurrent agent access interrupt delivery. Redirect and popup SSO journeys support fresh, explicit account selection at each actual login origin; credentials are never automatically shared and affiliation is never inferred. Iframe login forms, foreign-origin form destinations, automatic cross-origin account selection, address/payment autofill, and cross-device sync are not implemented.

**Automatic save/update offers** run only with the vault already unlocked, on the active visible tab with agent access off. Unlock before signing in. Detection uses a dedicated isolated world and a main-process binding; no credentials pass through the app renderer or sidecar. It observes a trusted click/key gesture followed by a same-origin POST form submission, using the same field-visibility checks as manual filling. Same-origin username-first/password-second forms are supported within one minute. Passwords marked `new-password`, ambiguous fields, GET forms and cross-origin actions are excluded.

The submitted form must disappear and visible password/error fields must be absent before an offer appears. This is a conservative heuristic, not proof of authentication: the native prompt asks you to confirm sign-in succeeded. It offers Save/Update, Not now, and Never for this site; unchanged saved passwords produce no prompt. Updating preserves the credential ID and aborts if another operation changed the stored login while the prompt was open. No credential is written without consent and the original vault grant. Locking, hiding, switching tabs, agent access, navigation during a prompt, or timeout discard pending work. Browser settings can disable offers or remove site exclusions. Exclusions are ordinary profile preferences, not encrypted account records.

Formless JavaScript sign-ins, persistent/hidden login forms, cross-origin SSO, iframe forms, password-change forms with multiple password fields and unusual success/error UI may require manual saving. Failed sign-ins without recognizable error UI can still produce an offer; decline it. Temporary submitted credentials exist in main-process memory for up to one minute while eligible; JS strings are not guaranteed to be zeroized. Captures already dispatched from the isolated world cannot be recalled, but main rechecks the vault/access state before retaining or saving them.

**Guided export imports (#22)** use the Import panel's password CSV, cookie JSON and bookmark HTML buttons, followed by a native file picker and default-Cancel review before writes. Review shows valid, duplicate, add, replace, unchanged and unsupported counts as applicable, plus category scope and the plaintext-export warning. Only the shared CookieMonster browser profile changes, not app/WPP data or page/vault grants. No browser profile scraping, protected-database reading or OS bypass is provided.

Password CSV imports match normalized origin/username, retain existing account IDs and skip exact duplicates. Password and cookie source conflicts use the last row; cookie replacements, including session credentials, are explicit in consent. Bookmark imports keep existing normalized URLs and their titles, IDs and pins; new URLs use the first row. Password/bookmark changes use one strict atomic store write. Cancelling review makes no import writes, including no legacy-vault migration.

Cookie JSON accepts an array of objects with `domain`, `name`, `value`, and optional `path`, `secure`, `httpOnly`, `hostOnly`, `sameSite`, `expirationDate`, `session`. Accepted IPv4 domains, with or without a leading dot, normalize to Chromium's host-only identity before review, deduplication and destination checks. DNS host-only/domain scope remains distinct; DNS domain matching ignores case and an optional leading dot. Noncanonical IPv4 and IPv6 representations remain unsupported. Unknown fields, partition/container scope and unsupported flags reject the whole import rather than broadening scope. CSV parsing reuses `csv-parse`; insecure non-loopback password URLs are rejected. Files are limited to 5 MB, with 2,000 password/bookmark or 5,000 cookie rows. Plaintext exports remain on disk until the user removes them.

Native results report category counts. Cookie results distinguish successful, failed and unattempted writes and whether flushing succeeded; a failed flush does not claim durable saving. Cookie writes are sequential and may be partial: successful writes are flushed even after interruption, with no rollback or automatic replay. Original window/task/renderer and password-vault access are rechecked across awaits. A changed reviewed destination requires fresh review, with relevant cookie destinations checked again before each write. This is process-local protection, not atomic cookie or multiprocess concurrency assurance. See [import evidence and limits](password-security.md#guided-export-imports-22).

**Clear browsing data** provides a category checklist and one native confirmation. Last hour, 24 hours, 7 days, 30 days, and all-time ranges apply to history and download records. Clearing history also removes matching recently closed tabs from memory and saved recovery. Electron does not expose time ranges for cache/site storage, so cache, cookies/site data (signing out browser websites), and passwords require all time; both UI and main enforce this. Open tabs and downloaded files remain. App and WPP login storage are separate.

The vault starts locked and requires Windows Hello or Touch ID to unlock. It locks again after a fixed five-minute interval, on device lock/sleep, hiding/minimizing/closing an app window, renderer teardown, or **Lock now**. Locked UI state contains no saved account metadata. Unsupported authentication setups (including Linux) stay locked. Windows development/packaging builds compile a small C++/WinRT helper with Visual Studio C++ tools and the Windows SDK; it ships under `resources/vault-auth`. macOS builds use Xcode's command-line tools to compile the AppKit account-entry helper into the same directory. Run `bun scripts/build-vault-auth.ts` if launching electron-vite directly instead of the normal predev step. Reauthentication is an app-level gate and does not add Windows app-bound encryption.

Main-process changes take effect on the next launch. Renderer hot reload can show the menu earlier; no running app or server is restarted by this implementation.

Development builds no longer open port 9222 automatically. `CM_REMOTE_DEBUGGING=1` explicitly enables it in development; saved logins are unavailable in that mode. Packaged builds do not enable that port through this variable.

The isolated `bun scripts/browser-smoke.ts --account-fill` verification covers explicit per-origin redirects and popup SSO, cancellation/retry and stale consent, with synthetic credentials. It distinguishes fixture failures from stale-consent rejection and inspects callback fields/tickets/submission state before closing, including a DOM-only negative control. See [#18 scope and evidence](password-security.md#explicit-cross-origin-logins-18) for the matrix and native/platform limits. Closure validation on 2026-09-22 passed this fixture on macOS arm64 / Electron 44.3.0 / Chromium 152.0.7977.78, plus 257 desktop browser tests, 19 browser-panel unit tests, 43 app browser tests and desktop/app typechecks. Dependencies #10/#17 are closed; independent correctness/spec and standards reviews found no acceptance gaps. This follow-up changes documentation only. Authentication and dialog answers remain controlled; real providers, physical accessibility, packaged builds, Linux and external security assurance remain separate work.

Encrypted password backup is available on macOS when the native secure-entry helper is installed. Each export/import requires a fresh device authentication; passphrases use a dedicated secure field, and exports never replace existing files. See [password backup format and limits](password-security.md#portable-encrypted-password-backups-32) and the [macOS validation record](macos-validation-2026-09-22.md).

## Browser settings

Settings reuse Electron session permission handlers and DownloadItem APIs. Camera/microphone rules are exact-origin, main-frame only, HTTPS or loopback, with Block/Ask/Allow. Ask uses a native prompt per request, and OS permission requirements still apply. Changing a rule requests a safety reload of matching open tabs, overriding reload vetoes but waiting for an outstanding agent close to settle. ## Agent uploads and downloads

Browser settings now include default transfer rules and exact-origin exceptions (scheme, host and port). Downloads support Ask (default), Allow and Block. Uploads support Choose files each time (default) and Block. Settings are validated and persisted in Electron main; malformed saved rules fail closed. These controls apply to tabs that have had agent access and connected opener/pop-up tabs for the rest of their lifetime, including delayed actions after access is revoked and manual transfers in those tabs. New unrelated private tabs keep normal browsing behaviour.

Downloads are checked at Electron's `will-download` boundary, including click, navigation and page-triggered downloads. Ask shows a native, default-cancel confirmation with the initiating page, filename and download URL before the ordinary save-location flow. Rules are keyed to the initiating page's origin, not the CDN/download URL. Allow still follows the user's Save dialog and destination preferences. Block or Cancel prevents saving; already active transfers use the existing Cancel control.

Uploads reuse Chromium's [file chooser interception](https://chromedevtools.github.io/devtools-protocol/1-3/Page/#method-setInterceptFileChooserDialog) and file-input delivery. Top-document file inputs open a native picker naming the receiving origin. Supported direct-child HTTP(S) iframe choosers use the tab grant without receiving-origin confirmation, then open the native file picker. Child selection requires current global/tab agent access and transfer policies at both boundaries; private, revoked and unsupported child choosers remain cancelled. The user alone chooses files; no agent API accepts local paths or initiates a child file-input click. A page can read selected files immediately and submit them through its own script. Navigation, access-revision changes, rule changes or window destruction while choosing discard the result; a fresh top picker after revocation retains existing private-browsing behavior. Concurrent pickers are suppressed, and pending child selection excludes agent page operations. Directory inputs remain unsupported; native chooser filters are not copied from the page. Losing interception closes the guarded tab instead of silently restoring unrestricted selection. This is file-selection consent, not a network upload firewall: it does not prevent a page from transmitting data it already holds.

## Agent history search

**Agent access to browsing history** is a profile-wide setting: Never, Ask each time (default), or Allow. It is separate from website consent in a tab; consenting to a history search can reveal saved visits to hosts the agent cannot browse. The global browser-agent switch also blocks these tools.

`browser_search_history` matches title or URL case-insensitively, with optional inclusive `from`/`to` Unix millisecond timestamps. It returns newest-first visits (including repeat visits), default 10 and maximum 20, with bounded titles, exact URLs and five-minute, task-bound result references. An oversized response fails explicitly rather than truncating URLs. Empty queries search all visits within the supplied dates. Ask uses a native default-cancel prompt displaying the query, UTC date bounds and result limit. History is read after approval. Pending approvals expire after one minute, and changing browser preferences invalidates pending approval and previously issued references.

`browser_open_history` accepts only a result reference from the same task and live app window. It always asks native confirmation showing the URL, opens a new tab with agent access off, and consumes the reference. Main rereads history before confirmation and before opening, so deleted visits cannot be reopened from an old result. Old browser builds reject these new operations. The tools work for tasks currently open in the app or with existing browser groups; unknown tasks cannot access the profile.

Deleting visits prevents future searches/opening through these tools. It cannot remove results already shared in chat. Search never exposes page bodies, vault data or a filesystem path. Native smoke coverage checks denied/allowed access, concurrent prompts, revoke/re-enable during approval, deletion while awaiting approval, cross-task references and private-tab opening.

`browser_drag({tabID, sourceRef, targetRef})` uses the same tab grant and source/access-bound preparation. Both distinct endpoints must be existing interactive refs from the same tab and retained snapshot. One synchronous isolated-world evaluation jointly applies the existing snapshot identity, ancestry, visibility, enabled and center-hit guards before any input, then again after the initial unpressed hover. Both centers must match their initial coordinates before press; moving targets are never chased.

The gesture sends one left press, four fixed interpolated pressed moves and one release. The exact original destination is revalidated at each movement boundary and before release, including its unchanged center; source movement after press is permitted. Changed or stale destination stops input without release, retry or `cancelDragging`, retaining quarantine unless release was acknowledged. Registration/owner, source/access, host policy and deadline are checked around every native await; busy/rendering/navigation ownership remains until native settlement. Already-dispatched effects cannot be recalled.

Success means the bounded pointer gesture completed, not that the site accepted a drop. Only snapshot-addressable controls are supported; plain noninteractive drop divs are not auto-discovered. Sites may use pointer capture or HTML5 drag loops. There is no arbitrary-coordinate or selector-discovery API, user duration/steps, universal HTML5 DnD, OS-file or native dragging.

`browser_select_option({tabID, ref, optionRef})` chooses an option owned by a native single-select ref from the same tab and retained snapshot. Collapsed options are metadata, not visible hit-test targets: only opaque ref, label, selected and disabled are returned, never option values. Metadata is capped at 50 options per select and 200 per snapshot with explicit truncation; main reenforces counts and 160-character labels. Iteration shares existing traversal budgets without allocating an unbounded option array. Labels use the option label attribute or safe text, excluding editable ancestry. Native option refs cannot be used for click, fill, hover or scroll.

Selection uses the tab grant and source/access-bound preparation. One fixed synchronous isolated-world script jointly revalidates document/snapshot, actual select and option weak-node identity, unchanged ancestry, ownership/membership, and the visible enabled hit-tested select. Dispatched effects cannot be recalled; failed acknowledgement or final snapshot never automatically retries selection. Existing deadline (including final capture), policy checks around awaits, busy-through-native-settlement ownership and input quarantine apply.

`browser_scroll({tabID, ref?, deltaX, deltaY, timeoutMs?})` sends one trusted Chromium wheel event. Both deltas must be finite integers in [-2000, 2000] CSS pixels and at least one must be nonzero. Without a ref, the event targets the viewport center; with a ref, it targets the center of that revalidated interactive element. Nested scrolling follows native hit testing, including scroll chaining at edges, site wheel cancellation and overscroll CSS. Empty/noninteractive containers cannot be directly targeted by ref. Successful dispatch does not guarantee movement or exact distance. Scroll uses the tab grant and source-bound preparation, with no automatic permission upgrade or down/up gesture.

`browser_wait_for_element({tabID, selector, timeoutMs})` observes the current top-frame document for a visible match. Only one ASCII compound selector is supported, at most 512 characters: an optional tag matching `[A-Za-z][A-Za-z0-9-]*`, followed by zero or more `#id` or `.class` tokens whose names match `[A-Za-z_][A-Za-z0-9_-]*`. At least one token is required, for example `button`, `#save`, `.primary`, or `button#save.primary`. In particular, correct and incorrect password-attribute guesses are both rejected, not distinguished by success versus timeout. The fixed isolated-world probe returns only boolean/status. Chromium IntersectionObserver supplies the actual viewport/clipping-chain intersection, including fixed elements escaping non-containing overflow ancestors, while `checkVisibility` checks opacity and CSS visibility. A positive intersection is not an occlusion or clickability guarantee. Iframes and shadow DOM are not searched. A fresh snapshot follows success, but a noninteractive match is not promised a ref.

`browser_wait_for_navigation({tabID, url, timeoutMs})` observes an exact URL and finished main-frame load. It is level-triggered: an already-loaded matching URL succeeds immediately, not proof of a new same-URL reload, network idle or application readiness. It never initiates, stops or vetoes user navigation. This is the only observation operation admitted during loading; current and target hosts, task registration/owner and access epoch remain checked around awaits, and destination URL/revision are pinned before final capture. Element waits and scroll instead reject any source epoch change.

One main deadline covers setup, probes, settling and final bounded snapshot, returning typed `timeout` or `cancelled`. Polling uses abortable main-process delays and short isolated-world IntersectionObserver samples, each with a timer capped at 100 ms and the remaining deadline. The sample disconnects its observer and clears its timer in `finally` before native settlement. Cancellation sends no cleanup or follow-on probe into the page; already-dispatched samples finish their own cleanup while busy/rendering ownership stays held. No persistent page listener or background polling service is installed. Results are observations, not guarantees that a dynamic page stays unchanged afterward.

Cancellation and deadlines end the agent reply without recalling an already-dispatched native command. Busy ownership, the rendering lease and navigation guard remain until that command settles. An interrupted key-down or mouse-press without an acknowledged release quarantines that WebContents: all subsequent agent page operations, including reads, write preparation and navigation, fail with recovery instructions. No automatic release is sent after cancellation or revocation because releasing can activate the page. **Close the affected tab, open a new tab and grant agent access again.** Reload, navigation, re-registration and access toggles do not clear quarantine. Closing still respects unsaved-page confirmation; neither cancellation nor quarantine rolls back page actions or disables manual input.

From `packages/desktop`, `bun scripts/browser-smoke.ts --cancellation` checks real Chromium key/mouse down events and button `:active` state, retained ownership while the driver completion is held, quarantine and new-view recovery. A fixture-only release demonstrates post-cancellation click activation. The fixture uses an isolated Electron profile and a deterministic completion hold, not physical input, naturally timed cancellation, or packaged-app/macOS/Linux assurance.

Agent success responses are checked as complete UTF-8 `Response` JSON against `MAX_SNAPSHOT_BYTES` (65,536 bytes), including page state, tab inventories, write preparation and history results. Oversized output returns `unavailable` with `Browser response exceeds the size limit.` Internal URLs remain complete for hashing and ref identity; no shortened URL is presented as an actual address. The existing page text/element reduction runs first. An oversized tab inventory fails as a whole, without pagination; recovery navigation to a short allowed URL still works with a known tab ID, otherwise the user must navigate manually. This bounds agent response data, not internal capture/storage, renderer state, the outer IPC envelope or plugin formatting. A response-size failure does not undo an already-dispatched action.

Main enforces the in-memory whole-tab grant in `registry.ts` for supported page tools and navigation. Issue #37 does not add frame discovery or interaction capabilities; those remain separately tracked. The legacy `cm-browser-allowlist.json` is not an access prerequisite. Agent navigation may change origins without another grant or tool approval. Grants are not persisted or shared with other tabs.

The renderer has only typed browser commands and fixed context operations, never an arbitrary JavaScript execution IPC endpoint. Main validates ownership against the app window's main frame.

## Unsaved-page leave confirmation (#48)

The native leave prompt is asynchronous, so a held decision does not block Electron's main event loop. Stay and cancellation preserve the current page. ### Inactive tab resource use (#47)

On native session recovery, the saved active tab is restored immediately. Other saved tabs keep their saved URL, title and supported navigation history as metadata, but their renderer is not asked to load until the user selects that tab or issues a native browser command for it. Restored tabs keep Agent Access off. An explicit navigation to a dormant tab replaces its saved destination; it does not first load the old page. No provider, tool or form submission is replayed.

This is lazy restoration, not page eviction. Once a recovered page has loaded, it stays alive when inactive so its live form state, page state and history are retained. The browser does not attempt to infer that arbitrary pages are safe to discard; consequently, memory can still grow with tabs the user has already visited. The policy applies only to saved recovery tabs, not busy/transferring/loading tabs or arbitrary live pages.

## Snapshot semantics (#14)

Snapshots use fixed top-frame code in a dedicated CDP isolated world, not page JavaScript or raw AX output. Naming is a pragmatic subset: same-root `aria-labelledby` (up to eight IDs), `aria-label`, native labels (up to eight), image alternatives, safe content, then title/placeholder fallback. Value-only submit/reset/button labels are deliberately omitted. It is not the full accessible-name algorithm. Native checkbox/radio and option states take precedence over ARIA; supported custom roles expose checked (including mixed), selected, expanded and disabled states. Disabled controls remain visible but ref activation is refused.

Capture visits at most 4,000 body/open-shadow nodes, with depth 64, a shared 4,000 naming/text-node visit budget and 48,000 text-character read budget. Output caps are 200 controls, 160 characters per name/text, 256 title characters and 12,000 aggregate text characters; main reenforces output bounds and reports truncation. Aggregate traversal visits light children once. Naming follows automatically assigned projected text/elements and nested open roots by scanning host light children for actual `assignedSlot` identity, sharing the naming budgets and seen set without allocating assignment arrays. Automatic slot fallback is used only after a complete scan proves no assignments; exhaustion marks truncation instead. Manual slot projection naming is unsupported: its contribution (including slot fallback) is omitted with truncation rather than guessed from DOM order. Title/placeholder fallback cannot replace an otherwise empty name after that omission; safe explicit names such as `aria-label` remain supported. Aggregate text traversal is not a guarantee of rendered projection order. Closed roots and iframes are excluded; noninteractive shadow content is best effort and does not imply a ref. Browser-native layout/DOM methods are synchronous and not preemptable; these are traversal/output bounds, not a hard renderer CPU bound.

Input/textarea values and editable content are never read as names, aggregate text or identity, including username, OTP, revealed-password fields, label descendants and editable shadow-host ancestry. Explicit page-provided labels and ordinary text are still untrusted content: a website can deliberately mirror secrets into them. This is not general data-loss prevention.

Refs bind tab/snapshot, document generation and actual node identity through isolated-world WeakMap tokens, with weak node/DOM-root/composed-ancestry references for ten retained snapshots. Generation/node tokens use 128 random bits from `crypto.getRandomValues`, including on insecure HTTP pages. Fill additionally requires the saved and current writable kind to match: supported input type, textarea or contenteditable mode. Changed text-to-submit, readonly, noneditable and fresh unsuitable targets fail before any click/key dispatch; an explicit click remains separate. Names, positions, selectors and ordinals are not identity. Reordering within unchanged ancestry may keep the original ref usable; identical replacements, currently disconnected nodes, changed ancestry/roots/hosts and missing mappings fail closed. Before coordinate input, the original node must remain visible, enabled and the composed-tree center hit target (or its ancestor). Covered/clipped centers fail closed. These checks are not atomic with subsequent native dispatch, do not track every transient DOM mutation between samples, and do not guarantee that page handlers retain the same meaning. Existing source/access epochs, cancellation settlement and input quarantine remain authoritative.

From `packages/desktop`, `bun scripts/browser-smoke.ts --snapshots` exercises production router snapshots and plugin rendering with synthetic sentinels, native/custom labels and states, duplicate reorder/replacement click witnesses, nested roots/slots/host changes, moved ancestry, disconnection, overlays, mapping eviction/loss, main-world monkeypatches and deep/multibyte output. The default full smoke also runs this fixture. These are isolated Windows Chromium checks, not packaged-app, physical-input, screen-reader, macOS/Linux or external security assurance.
