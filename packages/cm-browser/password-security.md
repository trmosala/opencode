# Password security

Status: hardened implementation with regression coverage and an [independent agent code review](password-review.md), **not an externally audited password manager**. Chromium-equivalent security has not been established. Security parity is a release requirement to assess against an explicit threat model, not a claim justified by encryption or passing tests alone.

## Portable encrypted password backups (#32)

The portable backup is deliberately separate from the live vault. It never exports the live vault ciphertext, its random AES key, or the OS-wrapped copy of that key. A backup contains only normalized website, username and password records; it excludes IDs, contacts, cookies, history, downloads, browser settings, permissions and app/WPP login data. Import assigns new IDs or preserves the destination ID for an existing origin-and-username match through the same reviewed merge path as CSV import.

The version 1 JSON envelope identifies `cookiemonster-password-backup`, uses scrypt with a 32-byte random salt (`N=65536`, `r=8`, `p=1`, 32-byte key) and AES-256-GCM with a 12-byte random IV and 16-byte tag. Fixed context plus the exact format, version, KDF parameters, cipher name and IV are additional authenticated data. Unknown fields, noncanonical base64, different parameters, oversized input, malformed records, wrong passphrases and any authenticated header/ciphertext change fail closed before the destination is read or written. The encrypted payload has its own format/version and creation time. Passphrases require 12 to 256 characters and are normalized with NFKC before key derivation.

Export and import both require an already-unlocked live vault and a fresh OS reauthentication for the operation. Passphrases use the non-persistent native Windows credential control; export requires two independent matching entries. The passphrase is not saved in CookieMonster, the OS credential store, the backup, logs or renderer state. Native passphrase entry is currently implemented only on Windows, so the UI disables backup operations elsewhere instead of presenting a control that cannot work. This is a platform limitation, not a security fallback.

Export writes a same-directory private temporary file, flushes it, then atomically publishes it with an exclusive hard link. It never replaces an existing file; a name collision or filesystem without hard-link support fails and removes the private temporary file. Cleanup after a committed publication is best effort, so an OS cleanup failure can retain a hidden encrypted temporary link beside the completed backup. Import reads at most 5 MB, fully authenticates and validates the backup, computes add/replace/unchanged/duplicate counts, and requires explicit native confirmation. It then rechecks window/task/vault ownership and an exact destination baseline before one atomic live-vault write. Cancellation, wrong keys, corruption, stale ownership and interruption before that write leave the live vault unchanged. Matching origin and username entries retain their destination ID; the last duplicate source record wins; changed passwords replace only after review.

The threat model covers a stolen backup file, accidental corruption, wrong passphrases, parameter downgrade, collision races and interruption before publication or import commit. Confidentiality depends on the user choosing a strong independent passphrase: anyone with the file can attempt offline guesses, and device authentication cannot protect a copied portable file. There is no forgotten-passphrase recovery. Losing the old OS keychain makes an unexported live vault unrecoverable; a previously completed portable backup remains recoverable with its passphrase and imports under a fresh key protected by the destination OS. A backup does not provide rollback, synchronization, multi-writer coordination, secure deletion of old copies, malware resistance on an unlocked machine, or external security assurance.

## Notification permissions (#23)

Both Electron permission hooks enforce exact HTTPS/loopback origin and the registered, attached, selected private main document. Workers, child frames, agent-enabled/busy/quarantined tabs, suspended/closing/recovering/reloading targets and unsupported native capability deny notification access. Saved Allow obeys the same scope. Ask uses a default-Cancel native dialog, with a 30-second limit, and saves Allow only after rechecking the original owner/task/tab/document/frame/access and policy revision. Navigation, task/tab/viewport changes, hiding, closure and policy changes settle pending callbacks once and remove listeners; late answers cannot revive consent.

Notification-only edits preserve camera/microphone rules without reloading media pages. Legacy camera/microphone rows default notifications to Block. Malformed stored rows deny access without overwriting the malformed data; explicit writes validate runtime values and reject corruption. Permission rules remain shared across browser tabs, not app/WPP partitions. Blocking affects subsequent permission checks; it cannot recall notifications already handed to the OS. Permission is not proof of OS delivery or instantaneous recall across an already-dispatched native operation.

The isolated Windows `--site-permissions` fixture exercises real Chromium `Notification.requestPermission()` and `Notification.permission`, but never creates or posts an OS notification. ## Guided export imports (#22)

The existing native picker now leads to a default-Cancel, count-only review for password CSV, cookie JSON and bookmark HTML imports. Parsed contents stay within one awaited main-process operation, never a renderer staging protocol. Review states the shared browser-profile category scope, plaintext-export caveat and deterministic conflict rules: last source row wins for passwords/cookies, while bookmarks preserve existing normalized URLs and use the first new source row. Password replacements retain IDs; unchanged imports skip writes. Legacy-vault previews do not migrate before consent. Password/bookmark commits use the existing strict atomic store.

One process-local import can be pending at a time. The original window/renderer, task epochs and password-vault generation are checked around picker/read/parse/review and cookie awaits. Window lifecycle listeners latch transient invalidation and are removed on settlement. Five minutes invalidates further work but does not forcibly close an outstanding native picker or cancel an already-dispatched OS operation. Reviewed category state is checked before commit; each pending cookie destination is checked again before its write. Unknown cookie fields, partition/container scope and unsupported flags fail closed. No page/vault permission expansion, external profile scraping or protected-database access is introduced.

Cookie writes remain sequential and non-atomic. Native results distinguish successful, failed and unattempted writes. Successful writes are flushed even after failure or owner invalidation; flush failure explicitly leaves durable saving unconfirmed. No rollback or replay is attempted. Native/parse/filesystem errors cannot echo imported records, values or full paths. Counts can still be reported after owner destruction. Already-dispatched effects cannot be recalled; check-to-write races, external writer A-B-A, multiprocess writers, physical disk durability and JavaScript-string zeroization are not guaranteed.

## Reused components and boundaries

- Node `crypto` / OpenSSL: AES-256-GCM, random keys and nonces. CookieMonster implements the storage envelope and integration, not the cryptographic primitives.
- Electron `safeStorage`: OS protection for each vault key. No plaintext fallback is permitted.
- Electron isolated worlds: fixed form inspection/fill code; page JavaScript has no desktop preload or vault API.
- Electron native dialogs: explicit, default-cancel save/fill consent showing origin and account. This is user consent, **not OS identity reauthentication**.
- OS reauthentication before unlocking: Windows Hello through Microsoft's `IUserConsentVerifierInterop` (only `Verified` succeeds), and Electron Touch ID on supported Macs. The Windows helper receives no credentials or encryption keys. Unsupported devices, Linux, cancellation, missing helpers and errors remain locked; there is no ordinary-dialog fallback.
- `csv-parse`: standard password export parsing; parser failures are replaced with a generic error that cannot echo records.

## Controls implemented

| Threat                                           | Control                                                                                                   |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------------- |
| Reading stored credentials without the OS key    | Entire credential payload encrypted, including origin, username and ID                                    |
| Editing a credential's destination or ciphertext | GCM authenticates the complete payload; unreadable data is not silently overwritten                       |
| Renderer access through generic settings         | Private browser namespace denied for get/set/delete/clear/keys/length, including Windows filename aliases |
| Page navigation during consent or filling        | Tab revision checks and one-use document-local tickets in the isolated world                              |
| Form replacement between inspection and delivery | Revalidate field identities, visibility, types and submission destination                                 |
| Hidden fields, ambiguous forms, credential URLs  | Reject obscured/invisible fields, multiple candidates, cross-origin actions and GET submissions           |
| Concurrent agent consent and password delivery   | Invalidate pending grants; block new grants while login operations are pending                            |
| Unintended password use from app renderer        | Each fill requires native consent; no password returned to app renderer; no automatic submission          |
| Local remote-debugging access                    | Development debug port opt-in; vault unavailable when port/pipe switches are present                      |
| Malformed/oversized imports                      | Bounded reads, batch validation, generic errors and atomic vault replacement                              |
| Interrupted migration or deletion                | One atomic store replacement updates the vault and removes legacy credential records                      |

Passwords necessarily reach the destination website after an approved fill. Website scripts can read, copy, reveal or transmit them. Field checks cannot defend against a compromised destination or XSS on the correct origin. Turning on agent access later grants access to that site's content; password-field snapshot redaction is not general data-loss prevention.

## Download persistence safeguards (#21)

Admission is persisted before destination setup; only current-process transfer IDs protect records from automatic pruning within the 200-record limit. Failed admission prevents saving. Failed terminal persistence retains the earlier interruption evidence, releases local control and does not automatically retry. Reopening records never restores grants, live control or requests. Supported transfers now retain restart-recovery metadata as described below; legacy records without that metadata remain retry-from-page only.

Completion checks regular-file size against received and known total bytes. Reveal checks available saved size/metadata; legacy records without identity metadata have weaker checks. Numeric filesystem metadata is not a cryptographic identity or race-free ownership mechanism, and checking a path cannot prevent later replacement. Application cancellation therefore performs no unlink, even for an empty reservation. Chromium may separately delete its own transfer file; no universal partial-file preservation is claimed.

Isolated Windows worktree checks on 2026-09-17 passed with Electron 42.3.3 / Chromium 148.0.7778.218: desktop `bun typecheck`, `bun test src/main/browser/` (161 tests / 2,360 expectations), and one serial default `bun scripts/browser-smoke.ts` after the cancellation-fixture correction. Five-path Prettier and whitespace checks passed; root-scoped lint reported 62 warnings on unchanged lines and zero errors. Source-only review cleared this bounded slice, not full #21. Unit checks use production helpers, disposable files/store reopening and injected persistence failures. The rollover regression failed before live-record protection. Native testing first failed an obsolete expectation that cancellation removed the reservation. Its replacement redirects Chromium to a separate disposable path, populates/renames the original reservation and creates a replacement exclusively, then verifies both exact byte sequences survive, one cancelled record settles and further control rejects. Existing destination-collision checks remain.

The Windows checks above covered the earlier history-only implementation, not restart recovery.

The 2026-09-21 recovery implementation stores the source URL, initiating origin, chosen destination and directory identity, strong ETag, Last-Modified, length, checkpoint filename/offset and SHA-256 in the main-only browser store. URLs can contain signed query parameters or other secrets. This metadata, completed paths and partial bytes are plaintext, not vault-encrypted; cookie and Authorization headers are not copied into the record. The private directory uses mode 0700 and checkpoint/working files use 0600 where the platform honors POSIX modes. The renderer receives only ordinary progress fields and a derived resume-available flag, never the URL, path, validator or digest.

Fresh native consent precedes every recovery request. Current transfer rules, record identity and window lifetime are checked through streaming and before publication. The saved checkpoint must be a regular non-symlink file of the exact recorded length and matching SHA-256. The original destination directory must retain its identity. Chromium's authenticated session networking sends one conditional range GET; redirects are refused and the actual response must match all recorded validators/range/length before any response bytes are written. Recovery never reconstructs credentials, posts a form, opens a login window automatically or treats a 200 response as resumed content. A cancelled or unsupported recovery leaves the user-facing retry-from-page path. Successful recovery exclusively creates a numbered sibling instead of opening the original path for overwrite.

Linux/Electron 44.3.0 isolated checks on 2026-09-21 killed an owned child during a real native download and reopened the same temporary profile. Recovery made no request before consent, reused a persisted fixture login, reproduced exact bytes and preserved both an original-path replacement and a sibling collision. Tests also rejected ignored ranges, changed ETag, redirects, edited partials, expired login and blocked rules; normal staged completion, native chooser cancellation and private-file cleanup passed. Unit tests cover missing/truncated/symlinked partials, response lengths/encodings, cancellation, record projection and publication collisions. These checks do not establish power-loss durability, concurrent profile writers, hostile same-user filesystem races, packaged Windows/macOS behavior or physical chooser usability. New English strings use the typed i18n layers; reviewed translations remain outstanding. #21 is implemented for this bounded scope, not closed or released.

## Remaining security limits

The vault starts locked. Successful OS verification grants a fixed five-minute window using a monotonic clock; passive status updates never extend it. Metadata, migration, reads, writes, saving, filling, deleting individual logins and importing passwords require an unlocked vault. Manual lock, OS lock/suspend, hiding/minimizing/closing an app window and renderer teardown lock it again. Lock generations invalidate pending authentication and asynchronous operations, even after another unlock. Explicit clear-all remains available while locked or corrupt with confirmation.

Locking prevents subsequent dispatch and clears account metadata from UI state. It cannot recall a credential-bearing script already dispatched to Chromium or a password already delivered to the page. Scripts check an execution deadline capped at five seconds and the remaining unlock interval; manual locking during that already-authorized interval is not a remote cancellation guarantee. Locking does not sign out websites or clear forms already filled.

1. **Windows same-user processes:** Electron's DPAPI model does not protect vault keys from other applications running as the same user. A native confirmation dialog does not fix this. App-bound key protection or a separately unlocked vault needs an evaluated design before claiming stronger local-process protection.
2. **App-level reauthentication versus key protection:** OS reauthentication and locking are application access controls. They do not change DPAPI/keychain cryptographic protection. There is no separate master password or hardware-bound vault key; the OS login/keychain remains the at-rest boundary.
3. **Local tools are not sandboxed by the browser permission switch:** a shell-capable agent or debugger running as the user is outside the browser-tool boundary and inherits the local-process limitation above.
4. **Memory and disk remnants:** temporary byte buffers are cleared where practical, but JavaScript strings and Chromium's delivered form values cannot be reliably wiped. Existing backups, filesystem remnants and user-created CSV exports are not securely erased.
5. **Legacy migration:** old records had unauthenticated plaintext origin/username metadata. Migration preserves their current contents and cannot establish that they were never altered before migration. Do not run an older build against a migrated profile: it does not understand this vault format.
6. **Availability and rollback:** local deletion, replacement with an older valid vault, OS-key loss and hostile same-user processes are not prevented. Corruption is surfaced without automatically resetting data; explicit clear-passwords remains available.

## Password generation (#8)
