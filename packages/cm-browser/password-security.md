# Password security

Status: hardened implementation with regression coverage and an [independent agent code review](password-review.md), **not an externally audited password manager**. Chromium-equivalent security has not been established. Security parity is a release requirement to assess against an explicit threat model, not a claim justified by encryption or passing tests alone.

## Reused components and boundaries

- Node `crypto` / OpenSSL: AES-256-GCM, random keys and nonces. CookieMonster implements the storage envelope and integration, not the cryptographic primitives.
- Electron `safeStorage`: OS protection for each vault key. No plaintext fallback is permitted.
- Electron isolated worlds: fixed form inspection/fill code; page JavaScript has no desktop preload or vault API.
- Electron native dialogs: explicit, default-cancel save/fill consent showing origin and account. This is user consent, **not OS identity reauthentication**.
- OS reauthentication before unlocking: Windows Hello through Microsoft's `IUserConsentVerifierInterop` (only `Verified` succeeds), and Electron Touch ID on supported Macs. The Windows helper receives no credentials or encryption keys. Unsupported devices, Linux, cancellation, missing helpers and errors remain locked; there is no ordinary-dialog fallback.
- `csv-parse`: standard password export parsing; parser failures are replaced with a generic error that cannot echo records.

## Controls implemented

| Threat                                           | Control                                                                                                   |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------------- |
| Reading stored credentials without the OS key    | Entire credential payload encrypted, including origin, username and ID                                    |
| Editing a credential's destination or ciphertext | GCM authenticates the complete payload; unreadable data is not silently overwritten                       |
| Renderer access through generic settings         | Private browser namespace denied for get/set/delete/clear/keys/length, including Windows filename aliases |
| Page navigation during consent or filling        | Tab revision checks and one-use document-local tickets in the isolated world                              |
| Form replacement between inspection and delivery | Revalidate field identities, visibility, types and submission destination                                 |
| Hidden fields, ambiguous forms, credential URLs  | Reject obscured/invisible fields, multiple candidates, cross-origin actions and GET submissions           |
| Concurrent agent consent and password delivery   | Invalidate pending grants; block new grants while login operations are pending                            |
| Unintended password use from app renderer        | Each fill requires native consent; no password returned to app renderer; no automatic submission          |
| Local remote-debugging access                    | Development debug port opt-in; vault unavailable when port/pipe switches are present                      |
| Malformed/oversized imports                      | Bounded reads, batch validation, generic errors and atomic vault replacement                              |
| Interrupted migration or deletion                | One atomic store replacement updates the vault and removes legacy credential records                      |

Passwords necessarily reach the destination website after an approved fill. Website scripts can read, copy, reveal or transmit them. Field checks cannot defend against a compromised destination or XSS on the correct origin. Turning on agent access later grants access to that site's content; password-field snapshot redaction is not general data-loss prevention.

## Remaining security limits

The vault starts locked. Successful OS verification grants a fixed five-minute window using a monotonic clock; passive status updates never extend it. Metadata, migration, reads, writes, saving, filling, deleting individual logins and importing passwords require an unlocked vault. Manual lock, OS lock/suspend, hiding/minimizing/closing an app window and renderer teardown lock it again. Lock generations invalidate pending authentication and asynchronous operations, even after another unlock. Explicit clear-all remains available while locked or corrupt with confirmation.

Locking prevents subsequent dispatch and clears account metadata from UI state. It cannot recall a credential-bearing script already dispatched to Chromium or a password already delivered to the page. Scripts check an execution deadline capped at five seconds and the remaining unlock interval; manual locking during that already-authorized interval is not a remote cancellation guarantee. Locking does not sign out websites or clear forms already filled.

1. **Windows same-user processes:** Electron's DPAPI model does not protect vault keys from other applications running as the same user. A native confirmation dialog does not fix this. App-bound key protection or a separately unlocked vault needs an evaluated design before claiming stronger local-process protection.
2. **App-level reauthentication versus key protection:** OS reauthentication and locking are application access controls. They do not change DPAPI/keychain cryptographic protection. There is no separate master password or hardware-bound vault key; the OS login/keychain remains the at-rest boundary.
3. **Local tools are not sandboxed by the browser permission switch:** a shell-capable agent or debugger running as the user is outside the browser-tool boundary and inherits the local-process limitation above.
4. **Memory and disk remnants:** temporary byte buffers are cleared where practical, but JavaScript strings and Chromium's delivered form values cannot be reliably wiped. Existing backups, filesystem remnants and user-created CSV exports are not securely erased.
5. **Legacy migration:** old records had unauthenticated plaintext origin/username metadata. Migration preserves their current contents and cannot establish that they were never altered before migration. Do not run an older build against a migrated profile: it does not understand this vault format.
6. **Availability and rollback:** local deletion, replacement with an older valid vault, OS-key loss and hostile same-user processes are not prevented. Corruption is surfaced without automatically resetting data; explicit clear-passwords remains available.

## Account management work (#5, #34)

Windows-first account creation and replacement use a separate `windows-entry` helper with native CredUI controls. No existing password is sent to this helper. The entered value returns only through the child process pipe to main; child errors are replaced with secret-free errors and returned buffers are cleared. CredUI is configured not to persist credentials. OS vault unlock still precedes entry, and default-cancel native consent precedes persistence. Editing preserves the selected ID, rejects duplicate origin/username pairs and detects concurrent changes. The UI receives metadata only.

Native entry is currently Windows-only. CredUI accepts at most 513 username and 256 password UTF-16 units. Longer imported usernames start with an empty entry field so the user can explicitly replace them rather than silently truncate them; imported values remain intact on cancellation. macOS entry is not implemented; no renderer fallback is provided.

`bun scripts/browser-smoke.ts --accounts` is the focused synthetic fixture: actual encrypted storage, stubbed entry/OS ceremony/native consent, create/edit, duplicate and conflict rejection, cancellation, lock/re-unlock races, corrupt ciphertext/key/version refusal, and migration. Its setter-failure injection verifies failure propagation before persistence; the separate filesystem/interruption evidence below now covers the storage boundary.

### Strict persistence evidence (#34)

Only the entire `cm-browser` namespace uses the narrow synchronous JSON store in `packages/desktop/src/main/browser/store.ts`; other stores remain on `electron-store`. The existing filename, tab-indented JSON, literal keys, unknown fields during key mutations, and used get/set/delete/has/clear/whole-store API are retained. Each replacement uses a unique sibling temp opened exclusively with mode `0600`, a complete write, file `fsync`, close, then rename. There is no direct overwrite fallback under EXDEV or SNAP, no private Conf writer override, and no production filesystem monkeypatch. Malformed existing JSON or a non-object root refuses mutation, including whole-store replacement. Reads come from disk, not a success cache.

Fresh verifier processes compare the entire old/new file byte-for-byte and decrypt the expected vault through production `readLogins()`, including settings and unknown fields. Before-rename interruption leaves one complete exclusive temp; reopening ignores it and does not delete or recover it. The after-rename verifier sees the complete new store and the same untouched prior orphan.

The same fixture exercises the actual `readLogins()` legacy migration, not copied migration logic. Injected EXDEV rejects migration and preserves all legacy ciphertext/settings, including on fresh-process reopen. Successful migration and a further fresh reopen decrypt the new authenticated vault, contain no legacy credential key, preserve settings/unknown fields, and do not rewrite the migrated file. Close failures both before and after actual descriptor closure preserve the original; the latter also keeps an unrelated newly opened descriptor usable. ## Contact autofill (#6)

Contacts use OS-encrypted storage, separate from passwords, and the same unlock window. The app renderer receives contact data for editing only while unlocked; the agent browser plugin has no contact API. Explicit native preview lists the exact origin and field values before filling. Supported targets are visible top-frame fields with explicit autocomplete tokens in one unambiguous section/form, same-origin POST destinations, and exact select option values. International parts are preserved without US-specific rearrangement; multiline addresses require a textarea.

The isolated `bun scripts/browser-smoke.ts --contacts` fixture covers encrypted CRUD, stale revisions, corrupt-data preservation without disabling healthy passwords, cancellation, hidden/disabled/ambiguous fields, document/form replacement, navigation, lock/re-unlock, detached views, edits during delivery, and South African/Japanese address shapes. Authentication and dialog choices are simulated, not native UI evidence.

Contact changes are refused during final delivery. Like password filling, an already-dispatched script cannot be recalled on manual lock; its execution deadline is at most five seconds and never exceeds the unlock window. This is not instantaneous revocation. Native long/multiline/RTL preview readability, keyboard interaction and supported macOS/packaged builds still need validation. No browser-security parity claim is made.

## Registration and password changes (#7)

Automatic offers support one or two explicitly marked `autocomplete=new-password` inputs, with equal nonempty values when there are two, and optionally one explicit `current-password`. All password inputs must be visible and usable. Inputs marked `current-password` or `new-password` remain credentials regardless of display type: revealed/non-password-type credential inputs cause rejection and never become username candidates. Mixed marked/unmarked passwords, overlapping current/new tokens, multiple current passwords, mismatched confirmation and ambiguous usernames are rejected rather than guessed from field order. Only the new value is captured for these forms; the current password is not sent to main or used to identify an account.

A visible unambiguous username is confirmed in the existing native origin/account consent. Without a username, an additional default-cancel native chooser requires explicit selection from exact-origin saved accounts, even when there is only one. It shows at most five accounts, with complete usernames of at most 80 UTF-16 units and no control/format characters; empty, duplicate or oversized lists are refused, not truncated. Larger/unusable lists require manual account editing. Previous username-only login steps never supply the account for a new-password form. Selection alone never saves: final default-cancel confirmation follows, and concurrent edits are checked against the pre-selection credential snapshot.

Capture remains in the dedicated isolated world and main-process CDP binding, with secure-context, top-frame, same-origin POST and private-tab (agent access off) checks. Offers never submit a form. Every trusted resubmission replaces the pending attempt, including rejected submissions. Trusted `invalid` events for the form associated with the recent user gesture also revoke the candidate when browser constraint validation prevents `submit`; the isolated world sends only `null`, without reading or transmitting field values. Consumed/discarded offers release all retained password input references. Vault lock/re-unlock, navigation during either dialog and tab selection revoke consent. Existing success detection is a heuristic (form removal or same-origin navigation, no visible password/error fields, no observed load failure), not proof that the website accepted the password; final copy explicitly requires the user to confirm success.

## Password generation (#8)

The browser chrome Passwords panel offers Generate password with a length input (16-64, default 20) and a symbols checkbox (on by default). The typed renderer command carries only those settings and the tab ID. Main uses Node `crypto.randomInt` for unbiased alphabet selection; bounded whole-string rejection ensures each selected character class appears without assigning predictable positions. Alphanumeric output uses uppercase/lowercase ASCII letters and digits; the symbol option adds `!@#$%^&*()-_=+[]{}:,.?`. Incompatible requested lengths are rejected, never silently shortened or weakened.

Only one or two explicit `new-password` fields in one secure top-frame, exact-origin POST form are supported, optionally with one `current-password` field. All credential fields must remain visible, usable and password-typed. Multiple forms/credential groups, ambiguous usernames, mismatching original confirmation values, revealed/hidden/unmarked credentials and unsafe submitter destinations are rejected. The shared form-control enumeration includes image submitters omitted by `form.elements`, including external controls associated through `form`; generation snapshots include their identities, raw overrides and effective destinations. The #7 offer path and explicit login destination checks use the same enumeration. Shared visibility uses Chromium's `:disabled` matching, including disabled fieldsets and their first-legend exception. Explicit new-field minlength/maxlength limits are intersected with the 16-64 floor/ceiling. Pattern attributes and custom-validity errors are refused, not parsed or evaluated in main. Undeclared/server-side password rules cannot be inferred.

A one-use isolated-world document ticket captures field/form identities, original values, constraints and destinations locally; only numeric bounds and username-presence metadata return to main. Default-cancel native consent names the origin, length/range and character option before generation and delivery. Delivery revalidates the snapshot and visibility, then sets both new values before emitting any input/change events. Current-password values never return to main and are never overwritten. Tickets, their expiry timers, subscriptions and busy state are cleaned on completion/cancellation; no generated-secret cache is retained. JavaScript strings cannot be reliably wiped.

Generation requires enabled save offers and an origin not excluded from offers, checked before consent and again before dispatch without modifying preferences. Username-free changes also require a usable exact-origin saved-account list. Filling does not submit or persist: the user submits on the website, then the existing #7 heuristic offers separate native save/update confirmation (and explicit account selection when needed). Consent warns that saving is not guaranteed if the page cannot be recognized or the vault/tab state changes.

Vault-generation, tab/access revision, active session/view, window and document checks reject revocation before dispatch, including lock/re-unlock and tab/session switches away and back. Pending generation blocks concurrent delivery and agent enablement on that tab. Actual membership in the native window's child views is required, not just the cached attached-tab pointer. Before delivering generated fields, main explicitly awaits the watcher's CDP installation/arming acknowledgement while retaining generation busy/access serialization. Timer and handoff work are serialized; lifecycle revisions and vault tickets reject stale acknowledgements. Each capture grant remains at most one second (and no longer than the remaining unlock interval), normally renewed every 400ms. Renewal continues through generation delivery and asynchronous ticket cleanup while the view remains active/private and vault/offer permissions remain valid; it does not acquire the prompting slot. Prompting checks availability both before and after its asynchronous success check, so it cannot overlap generation's busy/access serialization. Generated delivery remains capped by the original acknowledged grant, the existing five-second ceiling and remaining unlock interval; renewal never extends that delivery deadline. A delivery script reaching its deadline rejects before writing. This is not an unconditional save guarantee: event-loop/CDP stalls can interrupt renewal, and capture pauses during native offer dialogs.

A superseded background refresh does not clear the newer candidate/context preserved by same-origin navigation. Error cleanup checks the refresh's lifecycle revision and context ownership; current permission revocation still clears state, and lock/re-unlock invalidates the vault ticket and candidate. A superseded partial installation drops only its still-owned context so the next refresh reinstalls before arming. Generation readiness callers still fail on a missing/stale acknowledgement rather than treating background supersession as successful readiness. Already-dispatched Chromium code cannot be recalled. A post-dispatch error does not prove the page stayed unchanged. Once authorized values reach a website, its scripts can copy/reveal/transmit them; later agent enablement and same-user local tools remain outside this guarantee.

## Selected login-offer patterns (#9)

Persistent login forms may now offer saving after a scoped trusted submission when the original password input remains visible, usable and password-typed but its value has been cleared by website script. This path requires exactly one credential field in the document, unchanged credential role, form identity/action/method, control identities and submitter destinations, and an unchanged visible username when present. It does not apply to registration or password-change forms. Trusted input edits revoke the pending login attempt. Visible `role=alert` or `aria-invalid=true` signals observed by the success check discard the attempt; removing that signal later does not revive it. Invalid resubmissions continue to revoke without transmitting values.

The selected formless JavaScript scope is deliberately native-backed: an unmodified, non-repeating trusted Enter key on an explicit `autocomplete=username` or `autocomplete=current-password` input, with at most one of each and no other text/email/password or credential-marked inputs in the document. All must initially be formless, visible and usable. Website JavaScript must associate those same fields, with unchanged types/roles and revalidated visibility, with an exact-origin POST form and call `requestSubmit()` before the zero-delay gesture expiry runs. Only the resulting trusted native `submit` can capture credentials. Enter retains references and role/type metadata only, not password values; the gesture is consumed by submission or invalid validation. The browser never creates or submits a form for the website.

Fetch/XHR-only authentication, arbitrary button clicks, delayed/asynchronous association, unmarked fields, shadow DOM/iframe credentials and formless registration/change flows remain excluded. A declared native action does not prove the destination of arbitrary website JavaScript requests, and no network monkeypatch or network-body collection is added. This supports a small native-backed subset, not general SPA login detection. Same-origin username-only then password-only native-backed steps reuse the existing bounded main-process username handoff; new-password forms still never inherit it.

Both paths reuse the isolated watcher, main binding, vault lifecycle checks and default-cancel native consent. The existing English `nativeT` copy is unchanged: "Only save if this sign-in succeeded." Clearing a password can happen on failure as well as success; it is an offer heuristic, not authentication proof. HTTP 200, DOM text, a hidden form or a route change without a captured submission does not create an offer. The existing polling/grant limits remain: rejection signals that appear and disappear between actual checks, including during event-loop/CDP stalls, can be missed. A rejection already observed by a completed check is not covered by that limitation: it discards the still-owned candidate in the same context even if same-document routing occurs before acknowledgement processing. Website scripts already have access to website fields. No plaintext cache, renderer credential payload or page-visible vault API is introduced.

The shared asynchronous snapshot cleanup checks that ID in the original isolated context before releasing input/login references, so cleanup for an edited, rejected, consumed or revoked attempt cannot erase a newer submission's snapshot. This adds only identity metadata, not another plaintext credential cache. Trusted edits still clear the old local snapshot immediately and revoke its main-process candidate.

Same-document hash/history navigation retains the isolated context and snapshot for a fresh success check, while incrementing capture/security revisions and aborting open consent. Cross-document navigation still releases the old snapshot/context; only the existing exact-origin candidate handoff remains eligible for the new document's checks. Persistent-form revalidation compares effective control destinations: explicit `formaction`/`formmethod` overrides when present, otherwise the form action/method.
